# Plan — Lot 2 : finitions joueur, « Suivre ce coupon », chasseurs en ombre (une PR)

## Context

La PR #275 (produit & UX) est fusionnée et déployée en v11.25.0 le 28/10. Nouvelle règle de travail donnée le jour même : **un grand lot = une branche partie de `main` = une seule PR**, ouverte après un `/code-review`.

Choix de l'utilisateur pour ce lot (28/10) :

- **Contenu** : finitions joueur et chasseurs, dans la même PR, avec « Suivre ce coupon ».
- **Sécurité** : traitée dans le lot, pas en PR séparée.
- **Mesures historiques** : afficher la fréquence du marché et le réalisé, sans verdict. La probabilité du moteur sort de la vue joueur.
- **Suppression d'un coupon** : possible seulement avant le premier coup d'envoi.

L'exploration a aussi trouvé une faille. `etl`, `betting-engine`, `backtest` et une partie de `risk` n'ont aucun garde, sur une API publique. `GET /fixture` et `POST /channel-decisions/settle-range` sont ouverts à tout joueur connecté. `PATCH /auth/me/identity` change l'e-mail sans mot de passe ni code.

**Hors lot, noté pour la fin** : optimiser les images Docker. Le déploiement prend 9 min 22 s, dont 6 min 24 s sur le serveur (mémoire `project_deploy_images_slow`).

## Règles du lot

- Branche `feat/lot-2-joueur-chasseurs` depuis `main` à jour.
- Commits petits et autonomes (un constat ou une correction par commit), poussés au fil de l'eau.
- Une seule PR vers `main` à la fin, étiquette `minor`, modèle de PR en anglais.
- Respecter `docs/review-expectations.md` en écrivant, pas seulement en revue :
  - argent rejouable ;
  - un compte et ses montants portent sur les mêmes objets ;
  - inconnu ≠ 0 ;
  - jobs datés et retards ;
  - Decimal ;
  - aucun appel Prisma hors repository ;
  - types de retour explicites ;
  - mocks à la forme réelle.
- Vérifications à chaque commit :
  - backend : `pnpm --filter backend lint`, `typecheck`, puis vitest lancé directement ;
  - web : `.git/evcore-check.sh web <fichiers>` ;
  - après une modification d'analysis-core ou du schéma : `pnpm --filter @evcore/analysis-core build` et `pnpm --filter @evcore/db build`.
- Les migrations sont appliquées au démarrage du backend (`entrypoint.sh`). On ne les lance jamais à la main en prod.

## Étape 1 — Pause et restes de la revue

- **Pause posée au niveau de la classe** sur `channel-decision.controller.ts` (une fois settle-range devenu admin) et `fixture-scoring.controller.ts`.
- **Historique pendant une pause : rien à changer.** `GET /coupons` refuse aussi les jours passés, mais le web masque volontairement le bloc « Hier » et toute la page Coupons pendant une pause (choix de jeu responsable du 28/10). « L'historique reste ouvert » vise Mes coupons, Suivi de mise et Mesures historiques, qui restent servis. Ouvrir les jours passés côté serveur n'aurait aucun usage.
- **Montants formatés à un seul endroit.**
  - Nouveau `formatMoney(value: number | string, currency, opts)` dans `packages/analysis-core/src/display/money.ts` : fr-FR, XOF sans centimes, symboles F/€/$, espace insécable, arrondi à l'unité la plus proche (moitié éloignée de zéro), jamais « -0 », signe sur demande, symbole USD avant le signe.
  - Il est utilisé par :
    - `apps/web/helpers/number.ts` (`formatCurrency` et `formatSignedCurrency` délèguent ; le web garde la notation compacte) ;
    - `slip-digest.compose.ts` ;
    - `bankroll.service.ts`, dans le message de plafond (son défaut EUR disparaît) ;
    - `bet-slip.service.ts:191`.
  - Tests dans analysis-core.
- **`composeDouble` sans boucle complète** (`packages/analysis-core/src/coupon/double-composer.ts`). Les jambes sont triées par probabilité décroissante :
  - pour un `i` donné, la première `j` valide est la meilleure, on arrête donc la boucle intérieure ;
  - la boucle extérieure s'arrête quand `fair_i × fair_{i+1}` passe sous le meilleur score.

  Même résultat sur les specs existants. Mesure avant/après avec le script de bench du 28/10 : 505 ms au départ.

## Étape 5 — Supprimer un coupon saisi par erreur ; déclarer un retrait

- **Migration** : `BankrollTransactionType` gagne `SLIP_CANCELLED` et `WITHDRAWAL`.
- **`DELETE /bet-slips/:id`** :
  - **Autorisation** : uniquement pour le propriétaire, et seulement si toutes les jambes sont `PENDING` et si aucun match n'a commencé (`min(fixture.scheduledAt) > now`). Sinon 409 avec la raison.
  - **Une seule transaction** :
    - une ligne `SLIP_CANCELLED` qui rend la mise entière (mise unitaire pour un combiné, somme des mises pour des simples, en Decimal) ;
    - la suppression du `BetSlip`, en cascade jusqu'aux items et au placement ;
    - la suppression des paris utilisateur qui ne servent plus à aucun autre coupon (jamais un pari moteur, `userId` nul).
  - **Rejouable** : un deuxième appel répond 404 et n'écrit rien. Comme les items disparaissent, le règlement ne crédite plus jamais ce coupon.
  - **Web** : bouton « Supprimer ce coupon » dans `bet-slip-detail-panel.tsx`, avec confirmation, visible tant que c'est permis. Il rafraîchit les clés listées dans `bet-slip-drawer.tsx:409-416`.
  - « Corriger » un coupon revient à le supprimer puis à le ressaisir : la cote vient toujours du serveur.
- **`POST /bankroll/withdrawal`** :
  - `WithdrawDto` sur le modèle de `DepositDto`.
  - Une ligne négative, avec la vérification du solde **dans la même transaction** que l'écriture.
  - Le résumé expose `withdrawn`.
- **Web Suivi de mise** :
  - `deposit-dialog.tsx` devient une boîte avec un mode dépôt ou retrait ;
  - libellés et détail ajoutés pour `WITHDRAWAL` et `SLIP_CANCELLED` dans `bankroll-constants.ts` ;
  - option de filtre ;
  - textes dans `bankrollPage.withdraw.*`.
- **Tests** : suppression permise, refusée après le coup d'envoi, refusée si une jambe est réglée, pari partagé conservé ; retrait au-delà du solde ; deux retraits simultanés.

## Étape 7 — Chasseurs BTTS et Nul en ombre

- **Mécanisme d'ombre** :
  - **Migration** : colonne `shadow Boolean @default(false)` sur `coupon_proposal`.
  - `GET /coupons`, le relevé (`track-record`) et la page Coupons excluent l'ombre pour un non-admin. L'admin la voit avec l'étiquette « Ombre ».
  - Le règlement et la CLV par jambe existants s'appliquent sans changement : c'est la raison de réutiliser `coupon_proposal`.
- **Classes** dans `coupon-classes.ts` :
  - `HUNTER_BTTS`, une jambe sur la bande 1,45–1,90 ;
  - `HUNTER_DRAW`, une jambe sur la bande 2,90–3,60.

  Chacune a un `targetOddsMin` distinct, à vérifier contre `classForTargetOddsMin` et les coupons déjà en base, comme pour DOUBLE.

- **Compositeur** `packages/analysis-core/src/coupon/hunter-composer.ts`, fonction `composeHunter(candidates, hunterClass, ranking)` qui choisit une sélection par jour ou s'abstient. Deux variantes, rangées par la `source` existante, ce qui évite de toucher à la clé unique :
  - `PRICE_COMPOSER` : tout ce qui est coté sur le marché dans la bande, classé par probabilité du marché (`priceOutcomeGroups`), à égalité la marge la plus basse ;
  - `ENGINE` : les sélections du canal (BTTS, DRAW) du jour dans la bande, hors AVOID, classées par probabilité calibrée canal × compétition, puis par marge.

  Jamais d'edge. Exclusions : marché suspendu, match signalé « Données suspectes ».

- **Génération** : nouveau `coupon-hunter-generation.service.ts` appelé par `CouponDailyGenerationService` (passe isolée par `guard`). Il écrit `shadow: true` et une tentative par passe dans `coupon_generation_attempt`.
- **Première lecture immédiate** : script de rejeu `docs/audits/<date>/scripts/hunters.py` sur la copie de prod locale (116 jours), sur le modèle de `SELECTIONS-LAISSEES.md`.
  - Il mesure, par jambe, l'écart entre le réalisé et le marché, et entre le réalisé et l'annoncé, avec intervalle à 95 %, pire série et coût au prix d'analyse, pour chaque variante.
  - Rapport `HUNTERS.md`.
- **Porte d'affichage**, plus tard et hors lot :
  - au moins 4 semaines d'ombre prospective ;
  - au moins 200 jambes réglées en comptant le rejeu ;
  - réalisé ≥ 0,90 × annoncé ;
  - CLV publiée ;
  - décision de l'utilisateur.
- **Tests** du compositeur : choix dans la bande, abstention, exclusion des marchés suspendus, départage par la marge.
